# Stage 04 — Regions

> Turns a per-pixel palette label into a set of connected, single-ink faces: speckle gone, anti-aliasing folded into its neighbours, disconnected same-colour shapes told apart, and pixel-corner ambiguities resolved by the image.

**Source:** `crates/inkvec-trace/src/regions.rs` (connected components in `crates/inkvec-trace/src/regions/components.rs`), called from `crates/inkvec-trace/src/lib.rs`
**Entry point:** `trace_color_full_with_alpha()` (`lib.rs:285`), stages within it; the saddle pass runs at the head of `finish_color_trace_alpha()` (`lib.rs:1044`)
**Pipeline position:** after `color::label_image` (mark `"labels"`, `lib.rs:528`), before `gradient::merge_gradient_bands_with_ink` (mark `"merge_bands"`, `lib.rs:599`). The `split` sub-stage runs later, after stage 05's `carve` (`lib.rs:669`), and the saddle pass after it, just before `planar::build` (mark `"build_map"`, `lib.rs:1077`)

Fast mode has its own face writer (see [14-fast-mode.md](14-fast-mode.md)).

## What problem this solves

`color::label_image` assigns every pixel the palette entry nearest its measured colour. That is a per-pixel decision with no notion of shape: it does not know that a pixel is noise, that a run of pixels is only anti-aliasing between two real inks, that two blobs of the same colour on opposite sides of the canvas are different objects, or that four pixels meeting at one corner might belong to a single connected mark. Each of those is a distinct failure mode, and each gets its own pass:

- **Speckle** — an isolated pixel or tiny cluster that landed on the wrong palette entry (JPEG ringing, a stray anti-aliased pixel) becomes its own face with its own boundary unless removed first.
- **Blend slivers** — anti-aliased pixels between two real inks are frequently nearest a *third* palette entry, not either of the two they are blending. Left alone they form thin sliver faces along every boundary in the image, each minting junctions the boundary fitter has to honour (`regions.rs:756-760`). Measured on `mosaic_grid6` (36 flat cells): 128 faces and 368 edges, where the truth has 37 regions (`lib.rs:535-540`).
- **Disconnected same colour** — palette labelling only records colour, not connectivity. Two separate shapes of one ink must become two faces, not one, or every per-face measurement downstream (including gradient fitting) is corrupted.
- **Bowtie corners** — where two arms of one shape (or two separate shapes) meet at exactly one pixel corner, the labels alone cannot say whether that corner is one connected mark or two shapes touching at a point.

## Inputs and outputs

Working state through this stage is `labels: Vec<u16>`, one palette index per pixel (`w * h` long), plus the palette `pal: color::Palette`, the composited sRGB image `rgb: &[[f32; 3]]` (composited onto white), the true alpha channel (`source_alpha` when its length matches, else `img.data[..][3]`, `lib.rs:542-547`), and `sigma_noise: f64` (from `coverage::estimate_noise`). All colour distances in this stage are plain Euclidean distances in sRGB `[0, 1]`, on purpose: anti-aliasing mixes encoded values linearly, so a blend pixel lies on the straight sRGB segment between its two inks (`regions.rs:23-28`).

- `despeckle` and `absorb_blend_slivers`/`reassign_blend_pixels` **relabel pixels in place** — the array stays `w * h` long, only the label at each pixel changes.
- `split_components` **changes the indexing scheme**: it turns the label map (one id per ink, or per label stage 05 minted) into a face map (a `u16` per pixel that is now a connected-component id), plus `face_color: Vec<usize>` mapping each face id back to the label it came from (`regions.rs:210-214`). `lib.rs:686-710` then gives each face its label's fill and maps a minted label back to its palette entry.
- `merge_saddle_faces` **may reduce the number of faces in use** by unioning face ids at resolved corners. Only `labels` is rewritten; `face_fill`, `face_color` and `n_faces` are returned unchanged, so absorbed faces keep their (now unused) entries (`regions.rs:75-77`).

## How it works

### Despeckle (`despeckle`, `regions.rs:1027-1053`)

4-connected components of the label array are found once, before any is absorbed (`regions::Components`, `regions/components.rs:1-20`: each row cut into runs of one label, every run united with the runs of the same label that overlap it in the row above by a union-find, the unions resolved in a second pass — the two-pass scheme of K. Wu, E. Otoo and K. Suzuki, "Optimizing Two-Pass Connected-Component Labeling Algorithms", *Pattern Analysis and Applications* 12(2), pages 117–135, 2009, applied to runs rather than pixels. The code names two adaptations: the image is multi-label, so "same component" means "same label and connected", and components are numbered in raster order of their first pixel, as the old flood fill numbered them. Member lists are built only for the components a caller selects). Any component smaller than `min_size` pixels is reassigned, whole, to the neighbouring label sharing the most pixel edges with it, read from the labels as they are at that moment, so a speckle absorbed earlier counts under its new label; ties go to the lower label (`commonest_neighbour`, `regions.rs:1055-1090`, `std::cmp::Reverse(lab)` at `regions.rs:1088`). A component with no neighbour (the whole image one label) is left alone, and `min_size <= 1` is a no-op (`regions.rs:1033-1039`).

`min_size` is `opts.min_region`, described below.

### Blend absorption (`blend_absorb`, `lib.rs:533-570`)

Two passes, both skipped when `INKVEC_NO_ABSORB` is set (`lib.rs:541`):

**`absorb_blend_slivers` (`regions.rs:754-820`).** Runs at most two rounds, because dissolving one sliver can leave a neighbouring one thinner or bounded by fewer inks (`regions.rs:768-771`). Each round finds the components once (`SliverRound`, `regions.rs:822-859`), visits them in raster order, and lets each edit be seen by later components in the same round. The three tests, each on counts rather than colours so that one noisy pixel cannot swing them, are listed on `absorb_sliver` (`regions.rs:673-752`):
1. **Thin**: fewer than 20 % of its pixels are interior (`5 · interior < area`; a pixel is interior when all its in-image 4-neighbours are in the component), and it has at least one neighbour. "A blob with a real interior is a shape, not a seam."
2. **Between few inks**: its three most-touched neighbouring labels (ties to the lower label) account for at least 80 % of its boundary contacts, and at least two of them have a palette colour (`regions.rs:710-735`). A seam between two or three inks qualifies; a crumb in a busy area does not.
3. **A blend of those inks**: at least 80 % of its pixels lie within `tol` of a convex `mixture()` of the neighbour inks (`regions.rs:741-747`). If any pixel is translucent (`alpha < 0.99`) and white is not already one of them, the white backdrop (`BACKDROP = [1.0, 1.0, 1.0]`, `regions.rs:418-419`) joins as a pseudo-ink, because a translucent edge composited onto white is a blend with white (`regions.rs:736-739`).

`mixture()` (`regions.rs:421-520`) explains a pixel's colour as the nearest point of any segment between two candidate inks or any triangle spanned by three, and returns the residual distance and the ink with the largest weight in that nearest mixture — "the ink the pixel 'mostly is'". Pairs and triples, because an anti-aliased edge pixel is a blend of two inks at a boundary and three where boundaries meet (`regions.rs:443-449`); the search is exhaustive (`O(k³)`), which is fine because callers pass at most five inks.

On success each pixel moves to its own dominant ink (`sliver_destinations`, `regions.rs:629-671`), so a seam between A and B is split down the middle rather than handed wholesale to one side. When the backdrop dominates, the pixel is a translucent edge fading to nothing and goes to the dominant *real* ink instead (or to the most-touched neighbour if that fails). The tolerance is `tol = max(3·sigma_noise, 0.025)` (`regions.rs:787`); the floor "keeps clean synthetic input, where σ is near zero, from rejecting blends over float rounding in the rasteriser" (`regions.rs:764-766`). Debug output for each rejection reason is available under `INKVEC_ABSDBG`.

**`reassign_blend_pixels` (`regions.rs:929-1025`).** The per-pixel sequel: after whole slivers are gone, single blend pixels remain along boundaries carrying a third ink's label. For `ROUNDS = 4` rounds (`regions.rs:958`):
- The candidate inks are the pixel's own label plus up to three other distinct labels among its eight neighbours, first found in the scan order NW, N, NE, W, E, SW, S, SE; with fewer than two labels the pixel stays. The backdrop is added when the pixel is translucent (`regions.rs:1002-1005`).
- The pixel moves to the dominant ink of its nearest convex `mixture()` of those inks (pairs and triples) only when all three hold: that ink differs from its current one; the residual `r <= tol` with the same `tol`; and `r < 0.5 · |c − own|`, "the blend explains the pixel at least twice as well as the ink it has, so a pixel that is a plausible match for its own ink is left alone" (`regions.rs:938-941`, test at `regions.rs:1018`).
- Each round decides pixels from the labels as the round found them, in parallel with `rayon`, and then applies the moves, so the result does not depend on scan order. A decision reads only the pixel's 3x3 neighbourhood, so after the first round only the neighbourhoods of the pixels that just moved are decided again (`relabel_rounds`, `regions.rs:861-927`); every other pixel would decide "stay" as it did before. "Not from the literature: a plain worklist, because the moves after the first round are few (on the screen set 94 % of them happen in round one)".

If either pass changed anything, `despeckle` is run again (`lib.rs:566-568`) to clean up whatever the reassignment left behind.

### Split into connected faces (`split`, `split_components`, `regions.rs:210-242`)

Flood-fills the label array into 4-connected components, numbered in raster order of each component's first pixel, producing a face id per pixel and `face_color` mapping each face id back to its label (`split_within`, `regions.rs:244-291`). 4-connectivity, not 8, is what the planar map and the boundary tracer assume: two same-ink pixels that touch only at a corner are two faces, and the corner is a junction (`regions.rs:216-217`). This is the step that turns "every pixel of this colour" into "this one connected shape". Skipping it merges *every* disconnected same-coloured shape into a single region — wrong for editing (an editor could no longer move one shape independently) and for measurement: concentric rings quantised to six palette entries put several non-adjacent annuli of slightly different colour into one "region", whose flat residual was then a thousand times what noise could explain, so the fill fitter explained the difference with a radial gradient (`lib.rs:672-681`).

**More components than face ids.** Face ids are `u16`, and `u16::MAX` is reserved for the outside of the image in the planar map (and for "not yet visited" here), so at most `MAX_FACES` = 65,535 faces (ids `0..=65534`) can be numbered (`regions.rs:205-208`). The split used to number the first 65,535 components and drop the pixels of every later one into face 0, which then held pixels of many inks scattered over the bottom of the image under the first component's colour: "a 1024 px RGB noise image (36 inks, 68,654 components) came back with exactly 65,535 faces, a 2.5 MB SVG and 15 minutes of work (r2-product, 2026-10-02)" (`regions.rs:219-230`). Now `split_within` gives up where the old loop started folding (`regions.rs:256-258`), and `split_components` first merges the smallest components into their neighbours with `cap_components` (`regions.rs:293-416`) and then numbers the result as usual (`regions.rs:231-242`). A map with at most `MAX_FACES` components takes exactly the old path.

`cap_components` works in rounds (`regions.rs:296-317`):
1. Find the components (`Components`). If there are at most `cap`, stop.
2. Take the `excess = count − cap` smallest, ordered by size and then by raster order of their first pixel, so the result does not depend on hashing or threads.
3. In that order, relabel each one with its commonest neighbouring label (the label sharing the most pixel edges, ties to the lower label), unless a neighbour was already relabelled this round, or it was itself chosen as some other component's target. Every component next to it that carries the chosen label is marked a target, which keeps its label for the rest of the round.

Each relabelling removes a component: a relabelled component takes the label of a neighbouring target, which keeps that label to the end of the round, so the two are one component afterwards; no two relabelled components touch, so no merge is undone by a later one; and the first component of every round can always be relabelled, so the rounds end (`regions.rs:312-317`; a `progress == 0` guard against looping forever stays at `regions.rs:411-414`). The code labels it "Method from: region merging on a region adjacency graph, smallest and most similar first", as in K. Haris, S. N. Efstratiadis, N. Maglaveras, A. K. Katsaggelos (1998), *Hybrid image segmentation using watersheds and fast region merging*, IEEE TIP 7(12), pages 1684–1699, <https://doi.org/10.1109/83.730380>; "Adapted: the merge order is size alone and "most similar" is the longest shared border (the labels carry no colour here), and the stop is the face-id limit rather than a dissimilarity threshold" (`regions.rs:328-333`). It is reached only past `MAX_FACES` components, "which no image in the benchmark sets comes near (the largest 2048 px input has a few thousand faces)" (`regions.rs:323-326`). With `INKVEC_DIAG` set, a split that capped reports how many components it merged (`regions.rs:237-240`). Fast mode's face writer calls the same `cap_components` ([14-fast-mode.md](14-fast-mode.md)).

Measured (w2-robust report, section 4, 2026-10-03): on the r2-product `noise_1024` image the trace went from 65,535 faces with face 0 folded to 65,511 connected faces, none folded; the fuzz image `noise_rgb_1024` to 65,524. Both still take 16-18 minutes, in the palette (450-650 s) and the emitter (400-520 s), not here.

### Saddle resolution (`saddles`, `merge_saddle_faces`, `regions.rs:46-203`)

**An experiment**: compiled only with the `research` feature (`regions.rs:78`, call site `lib.rs:1058-1072`), and even then a no-op unless `INKVEC_SADDLE` is set, or when the image is narrower or shorter than 2 px (`regions.rs:91-93`). See Environment overrides.

For every interior pixel corner `(i, j)` where `1 <= i < w`, `1 <= j < h`, look at the four pixels meeting there: `nw = (i-1,j-1)`, `ne = (i,j-1)`, `sw = (i-1,j)`, `se = (i,j)`.

1. Skip unless the four face ids differ across every pixel edge at the corner — `nw != ne && nw != sw && ne != se && sw != se` (`regions.rs:116`). This is the four-way junction the labels cannot resolve alone.
2. Skip unless the two **diagonals** carry exactly two distinct **inks** (palette indices via `face_color`), one ink per diagonal: `face_color[nw] == face_color[se]` and `face_color[ne] == face_color[sw]`, and the two inks differ (`regions.rs:119-125`). Faces with no ink and inks with no palette colour, or two inks closer than `1e-6` in squared distance, are skipped (`regions.rs:126-133`).
3. Compute the coverage of ink A (the NW/SE ink) over ink C at each of the four pixels by projecting its colour onto the segment between the two palette colours: `t(p) = clamp(((p − C) · (A − C)) / |A − C|², 0, 1)` (`cover`, `regions.rs:134-141`).
4. Evaluate the saddle of the **bilinear patch** through the four coverages (`regions.rs:144-151`):
   ```
   den = cnw + cse - cne - csw
   num = cnw*cse - cne*csw
   at_corner = num / den      (or the plain mean (cnw+cne+csw+cse)/4 if |den| < 1e-9: the patch has no saddle)
   ```
   The doc comment calls this "the asymptotic decider used to resolve ambiguous cells in marching squares" (`regions.rs:53-58`); it cites no paper. `at_corner > 0.5` joins the A faces (the NW/SE diagonal); otherwise the C faces.
5. Propagate the pixel noise through this: the noise projects onto the ink axis as `σ_t = σ / |A − C|`, and first-order error propagation gives `σ_corner = σ_t · |∇s|`, with the four partial derivatives `g` of `at_corner` with respect to the coverages, or `σ_t / 2` for the degenerate mean (`regions.rs:67-70`, `regions.rs:152-164`).
6. The reading is **decisive** only if `|at_corner - 0.5| > SADDLE_SIGMAS * sigma_corner`, with `SADDLE_SIGMAS = 3.0` (`regions.rs:40-44`, test at `regions.rs:165`): "three sigma of the propagated coverage noise. Below that the two readings are indistinguishable, and the corner keeps the junction it has always had." A perfect checkerboard corner (coverages 1, 0, 0, 1) gives `at_corner` exactly 0.5 by the formula, so it is never decisive and keeps its junction.
7. A decisive corner unions the two faces on the winning diagonal via union-find (`find`/`parent`, `regions.rs:95-108`; the larger root is pointed at the smaller, `regions.rs:182-186`).

After the scan, every pixel's label is rewritten to its union-find root (`regions.rs:193-195`). Absorbed face ids are left in `face_fill`, `face_color` and `n_faces`, unused, rather than renumbered (`regions.rs:75-77`).

`planar::build`, called immediately afterward (`lib.rs:1076`), is what turns a merged corner into two boundary points instead of one junction: `split_saddle_corners` (`planar.rs:182-267`) gives the two faces on the cut diagonal their own copy of a degree-4 corner when exactly one diagonal is a single face, and leaves a corner whose diagonals are both one face, or neither, as a junction (`planar.rs:232-234`). "Which diagonal is one face is settled upstream, in `merge_saddle_faces`, where the image can be consulted" (`planar.rs:204-207`). The rule is covered by `planar.rs`'s `saddle_tests` module (`planar.rs:1351-1430`): `four_inks_meeting_at_a_corner_stay_a_junction` confirms an unreadable four-way corner keeps its junction, and `a_corner_two_shapes_share_becomes_two_points` / `splitting_gives_each_shape_its_own_copy_of_the_corner` confirm that once one diagonal is a single face, the corner becomes two independent points, one per touching shape, and every edge still separates exactly the two faces it did before.

The `min_region` decision, quoted directly (`crates/inkvec-cli/src/pipeline.rs:162-172`):

> A 2px floor is appropriate for the continuous bilevel path, but in colour mode it lets anti-aliased edge samples become their own tiny faces. Those faces split a smooth shared boundary into a literal pixel staircase before fitting. Nine pixels removes that confetti on the grid canaries while long thin artwork remains intact; an explicit --min-area always wins for deliberately tiny art. A 9-pixel colour-mode floor was tried (2026-09-03) to absorb anti-aliased stair-step faces and measured worse on the full 980-icon set: objective 0.7885 vs 0.7673 with the 2 px floor, 508 icons worse / 171 better in dE00 - it erased real dots and thin details more often than it removed confetti. Blend absorption and residual carving handle the stair-steps at the label level instead. The default therefore stays at the --min-area value (2 px).

The comment reads in the order the idea was tried and then reverted; the operative fact is the last sentence — the shipped default is 2 px, and the 9-pixel floor is a recorded negative result, not a live option gated by any flag. Blend absorption (this stage) and residual carving (stage 05) are what handle the stair-step confetti instead. The relative floor in `price_in_raster_units` is the other side of the same record: "a flat 9-px colour-mode floor was tried on 2026-09-03 and measured worse ... A floor that rises only when the raster is measurably carrying surplus pixels cannot make that trade" (`crates/inkvec-cli/src/lib.rs:411-416`).

## Failure modes and edge cases

- **`mosaic_grid6`** (`crates/inkvec-trace/src/lib.rs:535-540`): unabsorbed blend slivers on a 36-cell flat mosaic produced 128 faces and 368 edges against a 37-region truth — the canonical example of why blend absorption exists at all.
- **Genuinely thin features**: a thin component whose colour is off every segment and triangle between its neighbours' inks fails the third absorption test and keeps its own label; a component with a real interior fails the first (`regions.rs:675-688`). No unit test in this crate names a thin-feature canary.
- **Translucent edges**: an outer-edge pixel composited onto white is a mixture with the backdrop; the backdrop is a candidate ink whenever any pixel in the group (or the pixel, in the per-pixel pass) is translucent, and a pixel whose dominant ink is the backdrop goes to the dominant real ink instead (`regions.rs:629-636`, `regions.rs:943-944`).
- **Deterministic tie-breaks**: `despeckle`, `cap_components` and the absorption tally break ties on the label value itself rather than on hash-map or thread order (`regions.rs:1086-1089`, `regions.rs:305-306`, `regions.rs:716`); the per-pixel pass decides every pixel of a round from the same snapshot, so the result does not depend on scan order or thread count (`regions.rs:944-946`).
- **More components than face ids**: before `cap_components`, every component past 65,535 was folded into face 0 (a 1024 px RGB noise image: 65,535 faces, a 2.5 MB SVG, 15 minutes, `regions.rs:221-225`). Now the smallest components are merged into their neighbours until the rest fit, and every face is one connected component of one label (`regions.rs:1286-1302`, a 300 x 300 checkerboard of 90,000 components). Widening face ids to `u32` was considered and dropped: it touches the planar map, boundary solve, fitter, emitter and CLI (w2-robust report, section 6).
- **Saddle pass in a research build**: joining two faces at a corner changes which faces the emitter's containment tree stacks and punches; the current source records no measurement of the pass's effect (see Open questions).

## Environment overrides

Since the settings cleanup (CHANGELOG, 0.2.0, *Changed*) the engine reads its environment through one helper (`inkvec_core::env`): a switch is off when unset, empty or `0`, and every variable is read once per process. Variables marked *removed* below are gone (their defaults are constants now); those marked *research build* are read only by a binary built with `--features research`. The full list, with what is left and why, is [`docs/internal/env-vars.md`](../internal/env-vars.md).

| variable | effect |
|---|---|
| `INKVEC_NO_ABSORB` | if set, skips both `absorb_blend_slivers` and `reassign_blend_pixels` (and the despeckle after them) on the classic path (`crates/inkvec-trace/src/lib.rs:541`) and their four-channel counterparts on the native-alpha path (`native.rs:884`) |
| `INKVEC_ABSDBG` | prints per-component rejection reasons from `absorb_blend_slivers` to stderr for components over 15 pixels: not thin, contacts too spread, blend fail (read at `regions.rs:788`, printed at `regions.rs:704-746` and `regions.rs:805-807`) |

| `INKVEC_SADDLEDBG` (*research build*) | prints, per decided or tied corner, the two ink ids, the corner value, its uncertainty and the verdict, then a count of the joins (`regions.rs:94`, `regions.rs:167-177`, `regions.rs:196-201`) |

## Open questions

- The `tol` floor of `0.025` sRGB (roughly 6.4/255) in both blend passes (`regions.rs:787`, `regions.rs:959`) is explained as a guard for near-zero `σ` on clean synthetic input (`regions.rs:764-766`), but the value itself has no stated derivation — **Unverified:** why this specific value rather than, say, `2/255` or `1/255`.
- `reassign_blend_pixels`'s `ROUNDS = 4` and the "at least twice as well" (`0.5 · |c − own|`) margin carry no stated derivation in the source; they read as chosen values rather than measured ones. The same holds for the absorption gates' fifths and the 0.99 translucency gate.
- `SADDLE_SIGMAS = 3.0` (`regions.rs:44`) is justified in the comment only as a standard three-sigma significance bar; the comment does not report a swept or rejected alternative value — **Unverified:** whether it was swept.
- The saddle pass is an experiment, compiled only into a research build and off there by default, and the current source records no measurement of its effect. The source once did: a comment on `merge_saddle_faces` in `crates/inkvec-trace/src/lib.rs`, added by `7e68839` (2026-09-08) and dropped when the module was split out by `9402826` (2026-09-12), read "231 of the 246 screen icons are untouched — but it does not yet pay for itself on the set: objective 0.4005 -> 0.4010, six icons better and nine worse. The nine are the emitter's containment tree being rewritten by a merge into the background". Both commits are only on the pre-squash history branch `backup/pre-cleanup-full-history`, not in the history this tree was built from, and the measurement was not repeated after the pass moved behind the `research` feature. A second comment of the same commit, at the relabelling, gave the "two men holding hands" icon as the example: the merge cost it 0.06 dE00, "only because the face absorbed was absorbed into the background".
- `cap_components` merges by size alone and by the longest shared border, with no colour test (the labels carry none at that point, `regions.rs:331-333`); on an image that reaches the limit, which specks are lost is decided by size and adjacency only. No image in the benchmark sets reaches the limit, so the choice has no measured effect on quality.
- Tests: `split_components` and `despeckle` have direct unit tests in `regions.rs`'s own `#[cfg(test)] mod tests` (`test_split_components_disjoint`, `regions.rs:1114-1122`; `test_despeckle_removes_single_pixel`, `regions.rs:1124-1131`); `the_split_below_the_limit_is_the_old_split` holds the split equal, id for id, to the old split on random maps below the limit (`regions.rs:1207-1217`); `capping_components_merges_whole_components_into_neighbours` (`regions.rs:1219-1284`) and `a_map_with_more_components_than_face_ids_is_split_into_connected_faces` (`regions.rs:1286-1302`) cover the cap. `crates/inkvec-trace/tests/components.rs` exercises the split end-to-end through `trace_color_full` (e.g. `concentric_rings_are_separate_faces_and_each_is_flat`, `components.rs:154`). `absorb_blend_slivers`, `reassign_blend_pixels` and `despeckle` are held equal to their flood-fill, every-pixel-every-round versions on random scenes by `regions/reference_tests.rs` (and the four-channel ones by `native/reference_tests.rs`). The `mosaic_grid6` case cited in `lib.rs` is a corpus-level fixture, not a unit test in this crate.
