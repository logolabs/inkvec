# Inkvec code-quality and architecture audit, 2026-09-26

Commit `386b661` (v0.2.0, branch `chore/quality-audit` from main). Engine workspace (13
crates, 66k lines of Rust incl. tests) plus Studio (`studio/core`, `studio/src-tauri`,
`studio/wasm`, 11.5k lines Rust, 14k lines TS). Every number below comes from a tool run
recorded under `raw/` next to this file; `SUMMARY.md` is the machine-written digest and
`tools/quality_audit/run.py` regenerates it. Measurements were taken on a shared, loaded
machine (other agents building, all tools at below-normal priority): wall-clock numbers
are upper bounds, CPU shares in profiles are unaffected.

## Executive summary

**What is good.** The crate graph is acyclic and the engine crates (`inkvec-core`,
`-fit`, `-trace`) depend on nothing but each other, `rayon` and `image`: no CLI, I/O or
UI crate leaks downward. `inkvec-trace` and `inkvec-fit` have no cycles between their
top-level modules. Duplication is very low (jscpd: 0.87 % of Rust lines, 0 % of TS).
Line coverage is 81.4 % (regions 82.2 %) from 453 tests that all pass. No RustSec
vulnerability or unmaintained notice in the default build; `unsafe` exists only in
`inkvec-ffi` (11 blocks). The server's request path has no `unwrap`/`expect`/`panic!`
(Semgrep rule, 0 hits). The default clippy set is nearly clean (61 warnings, 48 of them
the ratcheted `too_many_lines`). Complexity is concentrated rather than diffuse: 63 % of
the 3,404 production functions have cognitive complexity 0, and the top 5 % (170
functions) carry 60 % of all of it, so a short list of refactors buys most of the gain.

**What is wrong.** Three structural problems, each bigger than any single hotspot:

1. **The engine is configured through the environment.** 91 distinct `INKVEC_*`
   variables are read by `inkvec-trace`/`inkvec-fit` at 104 call sites, through four
   separately written `env_f64` helpers, some cached process-wide in `OnceLock`s. They
   switch whole stages on and off (`INKVEC_DECODE`, `INKVEC_STRUCTURAL`, `INKVEC_G1`,
   `INKVEC_SADDLE`, `INKVEC_NO_CARVE`...) and retune thresholds (`INKVEC_SIGMA_SCALE`,
   `INKVEC_BOPT_ITERS`, `INKVEC_SAME_INK_DE00`...). None of it is visible to the Options
   schema the bindings are generated from, the server, or the WASM build, and a user who
   happens to have one set gets different output from the same binary.
2. **Two copies of the colour pipeline.** `inkvec-trace/src/native.rs` (1,723 lines, at
   the file-length budget) is a four-channel re-implementation of the three-channel
   path: 13 of its 36 functions share a name with a function elsewhere in the crate
   (`extract_palette`, `absorb_blend_slivers`, `blend_pairs`, `reassign_blend_pixels`,
   `claim_spread`, `mixture`, `label_image`, `trace_color`...). jscpd does not see it
   because the identifiers differ (`px`/`rgb`), but a fix made to one path does not
   reach the other.
3. **The pipeline lives in the CLI crate.** `inkvec` (the Options API every binding is
   generated from), `inkvec-wasm`, Studio core, Studio desktop and Studio WASM all
   depend on `inkvec-cli`, and `inkvec` turns its Options into `inkvec_cli::Args` (first
   field `input: PathBuf`) to call `inkvec_cli::trace_image_sized`. Inside that crate the
   root module and six submodules form one import cycle, and `emit::emit_color` is a
   1,042-line function with 21 parameters and cognitive complexity 372, twice the next
   worst function in the workspace.

**Test effectiveness is weaker than coverage suggests.** On a systematic sample of the
core modules, cargo-mutants' tests caught only 41.2 % of 294 viable mutants (121 caught, 173 survived; 10 % in `native.rs`, 29 % in `multimodel.rs`): colour science (`de00`'s chroma/hue terms,
`oklab_to_rgb`), the segment-crossing predicates in the boundary solve, and the
multimodel arm polishing are executed by tests but not pinned by them.

**Performance.** On every input profiled, the segment fitter is the largest single
cost: `inkvec_fit::candidates::best_cubic` takes 34-50 % of all CPU on flat logos
(512 px and 2048 px), most of it in its point-to-cubic Newton projection
(`Cubic::dist2_from`, 25-34 % self), and ellipse candidate scoring another 16-20 %. On a
gradient-heavy emoji, gradient stop fitting (`gradient::stops::fit_piecewise`, 26 % self)
plus `powf` (13 % self, largely sRGB<->linear conversions of constant stop colours inside
the per-pixel loop) dominate. Palette, planar map, boundary solve, emit and svgmin are
each under ~9 % and are not worth optimising first.

## Architecture

### Crate graph

`raw/crates.svg` (DOT in `raw/crates.dot`). Normal dependencies between workspace crates:

```
inkvec-fit       -> core
inkvec-trace     -> core, fit
inkvec-svgmin    -> core, fit
inkvec-sr        -> trace                 (only for Rgba + load_image)
inkvec-restore   -> trace, sr
inkvec-fab       -> core, trace
inkvec-cli       -> core, fit, trace, sr, restore, svgmin
inkvec (API)     -> cli, sr, trace
inkvec-ffi/-py/-server -> inkvec
inkvec-wasm      -> inkvec, cli, restore, sr, svgmin, trace
studio-core      -> cli, core, fab, fit, restore, sr, svgmin, trace
studio (tauri)   -> cli, fab, restore, studio-core
studio-wasm      -> cli, fab, restore, studio-core, trace
```

- Acyclic, and the bottom three layers are clean. That is the most important property
  and it holds.
- The layering is inverted in the middle: the orchestration everyone needs is in the
  crate named `-cli`, and the public API crate `inkvec` sits *above* it and converts its
  Options into the CLI's `Args`. The rule "one Rust Options + generated schema" is kept
  for the bindings, but Studio and `inkvec-wasm` bypass `inkvec` and build `Args`
  directly, so there are effectively two option models (Options and Args) plus a third,
  invisible one (environment variables).
- Studio core reaches into eight engine crates. Some of that is legitimate (measuring,
  fabrication), but it compiles against engine internals rather than a stable surface.

### Module graphs

`raw/modules/<crate>_modules.svg` (module level; edge labels = number of `use` edges);
item-level DOT in `raw/modules/<crate>_items.dot`. Collapsed from cargo-modules' `use`
edges (fully qualified paths in code are not counted).

- `inkvec-trace` (31 modules, 467 items): no cycle among top-level modules. Hubs by
  fan-in: `color` (7), `gradient` (6), `planar` and `coverage` (5). Fan-out is highest for
  `native` (6): it is the second pipeline. `native` and `regroup` import from the crate
  root (`ColorOptions`, `ColorTrace`, `Stopwatch` live in `lib.rs`), so `lib.rs` is both
  the facade and a shared-types module. Cycles exist only between a module and its own
  children (`gradient` <-> `gradient::bands/carve/stops/svg`, `planar` <->
  `planar::junctions`, `decode` <-> `decode::ribbon`), which is normal Rust.
- `inkvec-fit` (17 modules): no cycles; eight modules import types from the crate root.
- `inkvec-cli` (11 modules): one strongly connected component containing the root and
  `emit`, `harmonize`, `pathdata`, `pipeline`, `rings`, `seams`. Without the root the only
  cycle is `emit` <-> `pipeline`, and it exists because `colour_name` is defined in
  `pipeline.rs:1165` and used by `emit`. The root cycle exists because the geometry types
  (`FaceRings`, `Layers`, `Ring`) are defined in `lib.rs` next to `cli_main`.
- `inkvec-svgmin`: `fit` <-> `path` cycle (small crate, low priority).
- `inkvec-fab`: clean; `geom` is the hub (fan-in 12).
- No orphan source files in any crate.

### Engine-layer smells (non-test library code)

| crate | env var reads | print/eprint | std::fs | unwrap | expect | #[allow] |
|---|---|---|---|---|---|---|
| inkvec-trace | 83 | 68 | 2 | 14 | 3 | 21 |
| inkvec-fit | 18 | 6 | 0 | 20 | 0 | 10 |
| inkvec-cli | 24 | 38 | 5 | 4 | 0 | 7 |

The engine prints its own diagnostics to stderr (68 sites in `inkvec-trace`, behind
debug variables such as `INKVEC_PALDBG`, `INKVEC_BOPTDBG`). A library printing to its
host's stderr is a CLI concern leaking down; the Studio and server hosts cannot capture
it. A diagnostics sink (a callback, or the `log`/`tracing` facade) would replace both the
prints and the debug variables.

Reading across the three:

- **The segment fitter is the bottleneck on flat art**, at every size:
  `candidates::best_cubic` is 34-50 % inclusive, with `Cubic::dist2_from` (3 Newton steps
  of Bezier eval + derivative per sampled point per candidate cubic) 25-34 % self. Ellipse
  candidates (`SpanScorer::ellipse` -> `fit_ellipse_algebraic`, `ellipse_chi2`,
  `EllipseFit::contact`) are another 18-20 % inclusive. This matches the earlier note that the real
  ceiling is the largest ring's `fit_dp`. Worth optimising (action 6): power-basis Horner
  evaluation, a DP-wide bound for the early exit in `CubicSamples::chi2`, and skipping
  ellipse scoring on spans whose circle fit (already O(1) from `CirclePrefix`) is hopeless.
- **Gradient-heavy input is dominated by stop fitting**: `merge_bands_with`'s parallel
  closure -> `fit_samples` is 55 % inclusive, `stops::fit_piecewise` 26 % self and `powf`
  13 % self. `lerp_stops` converts both end stops to linear light on every call although
  they are constant per model; `FillModel::color_at` is 16 % inclusive (action 7). This
  input is also the slowest per pixel: 2.5 s for 512 px against 2.1 s for the 2048 px flat
  logo.
- **Palette** (`color::*`): 3.5-8.9 %, mostly `rgb_to_oklab`'s `powf`; a 256-entry LUT is
  exact for 8-bit input. Cheap, modest.
- **Not worth optimising first**: planar map, boundary solve (under 3 %), emit, svgmin,
  image decode, symmetry, repair. rayon's idle spinning and parking
  (`NtDelayExecution`, `NtWaitForAlertByThreadId`) is 2-7 % of CPU.

## Latent bugs and risks found along the way (flagged, not fixed)

1. **Unbounded float loops.** `boundary_opt::crossings` (`boundary_opt.rs:196`, `:214`)
   steps `m += 1.0` while `m < hi`; a non-finite or very large (>= 2^53) coordinate hangs
   the trace and grows the crossing list without bound. Same shape in
   `inkvec-fit/src/lib.rs:199` (`wrap_near`), `primitives.rs:470`, `ellipse.rs:130`,
   `structural.rs:802`, `centerline/outline.rs:64`. Such coordinates should not arise, but
   nothing guards against them; an `is_finite` check on solver output would. The mutation
   run also shows the crossing predicates are untested.
2. **Environment switches disagree about what "0" means.** `INKVEC_BOPT=0` and
   `INKVEC_DECODE=0` mean off, but `INKVEC_NO_CARVE=0`, `INKVEC_NO_ABSORB=0` and
   `INKVEC_NO_FADES=0` *disable* their stage too (they test `var_os(..).is_none()`), and
   `INKVEC_NO_TAPER` is ignored when empty. Some are read on every call, some once per
   process (`OnceLock` in `candidates.rs:35,42,71`, `gradient/regions.rs:10`,
   `color.rs:64`, `junctions.rs:395`): in the long-running server or Studio, changing one
   has no effect until restart, while its neighbours take effect immediately.
3. **Research knobs sit in the default path**: `INKVEC_SAME_INK_DE00`, `INKVEC_MERGE_DE00`,
   `INKVEC_SIGMA_SCALE`, `INKVEC_BOPT_ITERS` are read by the default pipeline; a user or a
   CI machine with one set would move the gate without any code change.
4. **CIEDE2000 is only tested near the grey axis** (`color.rs:1433-1437`: four pairs with
   a, b ~ 0, tolerance 0.05-0.08), so errors in the chroma and hue-rotation terms pass.
   The mutation run confirms it: 7 mutants in `de00`'s chroma/hue arithmetic survive.
5. **A Studio test reads the real home directory** (`integration.rs:346`), read-only today.
